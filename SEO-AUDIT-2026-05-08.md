# SEO audit — londonchoralservice.com

**Date**: 2026-05-08
**Scope**: full site (99 indexable pages — 12 pillars, 53 location pages, 34 music guides)
**Audit method**: Phase 1 live discovery sweep + 9 parallel specialist sub-agents (claude-seo plugin) + inline cannibalisation and internal-linking analysis.

---

## Executive summary

The site is **better than average on fundamentals** — clean robots.txt and sitemap, server-rendered HTML on a fast CDN, every page indexable with correct canonical and OG metadata, every page carrying parseable JSON-LD, almost no images means CWV will pass without effort, AI crawlers explicitly allowed, and a thoughtfully written `llms.txt`. Content depth is strong (music guides average 2,068 words; area pages 900–1,400; pillars 600–2,200). The site has been built with care.

The audit found 55 findings across 13 themes (sections 1–12 plus a Section 13 supplemental from re-running incomplete specialists). Five are **load-bearing** — fix these first. Four of the five can be done in a single focused PR.

### Top 5 priorities (in fix order)

1. **CRITICAL — Sitewide AggregateRating violates Google's review-snippet self-serving rule.** The same `ratingValue: 5, reviewCount: 4` block appears on **all 99 indexable pages**, but only `index.html` and `about.html` actually display the reviews in body content. Google's policy explicitly prohibits aggregating reviews "site-wide" or onto pages that aren't the rated content. Risk ranges from silent rich-snippet suppression to a manual review-snippet action. Fix: keep the AggregateRating + review array on `index.html` only (and optionally `about.html`); remove it from the other 97 pages. **Effort: 1–2 hours; one-line schema change in the build pipeline.**
2. **CRITICAL — `corporate.html` has only 1 inbound internal link.** Verified: the only page that links to it is `services.html`. The third commercial pillar (out of three) has no exposure in nav, no music-guide cross-link path back, and is effectively a dead page in the link graph. Two of the four commercial pillars (`weddings.html` and `funerals.html`) get 14–17 inbound links. `corporate.html` and `christmas.html` are starved.
3. **CRITICAL — Global nav omits all 4 commercial pillars.** Verified in `partials/nav.html`: nav links to `/`, `/about.html`, `/services.html`, `/listen.html`, `/music-guides/` (with category-filter URLs), `/pricing.html`, `/contact.html`. It does **not** link to `/weddings.html`, `/funerals.html`, `/corporate.html`, or `/christmas.html`. The "Music Guides" dropdown points to filtered guide views — not service pages — so a visitor clicking "Weddings" gets a guide list, not the wedding service page. This is the single biggest internal-linking topology problem on the site.
4. **CRITICAL — Trust-signal scarcity vs directory marketplaces.** SXO analysis: directory aggregators (Encore Musicians, Alive Network, PopTop) own positions 1–8 for `wedding choir hire`, `wedding singers London`, and `Christmas carol singers hire`. They each carry 60,000+ platform reviews. The site's `aggregateRating` shows `reviewCount: 4`. Even if the 5-star rating is literally true, the rich-snippet renders as "5.0 (4)" — visually and numerically weaker than competitors. Plan a **post-event review-request workflow** targeting 30+ Google/Trustpilot reviews within 90 days; this is the single highest-leverage off-site action.
5. **HIGH — Title-tag truncation across 67 of 99 pages.** Template `Funeral Singers & Wedding Choirs in [City] — London Choral Service` is 64–72 characters depending on city name and exceeds Google's ~60-char SERP truncation point on every area page. Easy fix: shorten the brand suffix to `| LCS` or drop the brand suffix on local pages and let the H1 carry it.

### Quick wins (≤1 hour each, ≥medium impact)

- Remove `HowTo` schema from 9 music guides (deprecated for rich results since late 2023; zero benefit, ~1–3KB inert markup per page).
- Replace `ratingCount` with `reviewCount` on `weddings.html` and `funerals.html` (deprecated property name on `AggregateRating`).
- Add `priceValidUntil` to all 4 service pages' `AggregateOffer` blocks.
- Fix sitemap date typo on `popular-wedding-organ-music.html` (line 594: `2026-03-06` → `2026-05-06`).
- Replace `openingHours` legacy string with structured `openingHoursSpecification` on `index.html` and `contact.html`.
- Add the 21 missing music guides to `llms.txt` (currently lists 13 of 34).
- Add `<link rel="preload" as="font">` for the two woff2 fonts in `partials/nav.html` (HIGH-impact LCP fix from §13.3.1; ~10 minutes).
- Add `width` and `height` to all `<img>` and `<picture>` elements (CLS fix; §13.3.2).
- Add visible author byline below `<h1>` on the 3 sampled music guides — sweep the other 30 (§13.2.1).
- Update `robots.txt` with `Disallow: /*?utm_` etc. to protect crawl budget (§13.1.4).

## 1. Crawl & indexation health

### What's good (do not change)

- **Hosting + redirects**: GitHub Pages on Fastly. `https` enforced, `www` → apex on a single 301 hop, HTTP → HTTPS on a single 301 hop. HSTS active (`max-age=31556952`).
- **robots.txt**: live = repo. Explicitly allows GPTBot, ChatGPT-User, Google-Extended, ClaudeBot, PerplexityBot, Cohere-AI, Applebot-Extended.
- **Sitemap**: live = repo. 99 URLs, application/xml content-type, exact match to indexable pages on disk (zero orphans either direction). `noindex` pages (privacy, thank-you, 404) correctly absent.
- **404 handling**: `/this-does-not-exist` returns a real 404 (not soft-404). Verified: `curl -s -o /dev/null -w "%{http_code}\n" https://londonchoralservice.com/this-page-does-not-exist-test-404` → `404`.
- **Indexable pages**: every sampled page has `<meta name="robots" content="index, follow">` and self-canonical. `noindex` is correctly applied to `thank-you.html`, `privacy.html`, `404.html`.
- **Hreflang**: `en-gb` + `x-default` consistently set. Single-language site, correct.
- **Canonical handling for filter URLs**: `/music-guides/?category=funerals` correctly canonicals to `/music-guides/`. `/index.html` correctly canonicals to `/`.

### Findings

#### MEDIUM — Extension-less URL duplication (canonical resolves it, but link signals can leak)
- **Issue**: GitHub Pages serves both `/about` and `/about.html` with status 200 from the same content. Same for `/index.html` vs `/`. The canonical resolves the duplication for indexing purposes, but inbound links from external sites that drop the `.html` suffix would split signal across two URLs.
- **Evidence**: `curl -s -o /dev/null -w "%{http_code}" https://londonchoralservice.com/about` returns `200`; same for `/about.html`. Both pages serve identical HTML with `<link rel="canonical" href="https://londonchoralservice.com/about.html">`.
- **Fix**: Lower priority. If you ever switch off GitHub Pages, redirect extensionless → `.html` at the host. For now, canonical handles it.
- **Effort**: Not actionable on GitHub Pages without leaving the platform.

#### MEDIUM — Security headers absent (limits trust signals beyond SEO)
- **Issue**: `curl -sI` on the homepage and inner pages returns only HSTS and Cache-Control. No `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, or `Permissions-Policy`. Not direct ranking factors but they affect security-tool scorings used by buyer-procurement teams (see corporate persona below).
- **Evidence**: `curl -sI https://londonchoralservice.com/ | grep -iE 'x-frame|content-security|x-content|referrer|permissions|x-xss'` returns nothing.
- **Fix**: Partial mitigation via meta tags (`<meta http-equiv="Content-Security-Policy" ...>`, `<meta name="referrer" content="strict-origin-when-cross-origin">`). Full headers require leaving GitHub Pages.
- **Effort**: 1–2 hours for meta-tag mitigation; longer if migrating host.

#### LOW — HSTS could include subdomain/preload directives
- **Issue**: Current header is `strict-transport-security: max-age=31556952` (1 year). No `includeSubDomains; preload`.
- **Fix**: GitHub Pages doesn't allow custom HSTS headers; this is a hosting-platform constraint to note rather than fix.

#### LOW — Cache-Control max-age=600 (10 min) is short for static HTML
- **Issue**: GitHub Pages applies a 10-minute browser cache. Acceptable for a site that pushes content updates frequently, but means repeat visitors re-download HTML often.
- **Fix**: GitHub Pages constraint. Negligible at site scale.

## 2. On-page health

### What's good

- **Single H1 per page**: verified across all sampled pillars, areas, and guides.
- **All pages have title, meta description, canonical, hreflang, OG tags**: verified.
- **No duplicate titles**: programmatic check across 99 pages found zero duplicates.
- **No missing meta descriptions**: every page has one.
- **Heading hierarchies are sensible** on the pillar and guide pages.

### Findings

#### HIGH — Title tags exceed ~60-char SERP truncation on 67 of 99 pages
- **Issue**: Template `Funeral Singers & Wedding Choirs in [City] — London Choral Service` runs 64–72 chars depending on city name. Confirmed examples: `Funeral Singers & Wedding Choirs in Manchester — London Choral Service` (72 chars), `… in Birmingham — …` (70), `… in Canterbury — …` (70). Same pattern on all area pages and most pillars.
- **Evidence**: programmatic title-length scan across 99 indexable pages; 67 over 60 chars; longest 72.
- **Fix**: Two options — (a) shorten the brand suffix to `| LCS` (saves 18 chars), or (b) drop the brand suffix on local pages entirely (Google appends `… - {site name}` in SERPs anyway when needed, sourced from the site's `og:site_name`). Option (b) is cleaner and tested-good for local pages: e.g. `Funeral Singers & Wedding Choirs in Manchester` (47 chars).
- **Effort**: 1 hour if templated through `build.sh`.

#### HIGH — Area-page H1 is funeral-leaning despite dual-vertical title
- **Issue**: Every area page H1 reads `Funeral singers and choirs in [City]` (verified on Manchester, Oxford, London, Westminster, Havering). The title says "Funeral Singers & Wedding Choirs". The page covers both. The H1 is the strongest on-page entity signal — and it's funeral-only. Wedding-intent local queries (`wedding choir Manchester`, `wedding singers Oxford`) have a weaker case to rank these pages.
- **Fix**: Two paths. (1) Keep dual-vertical pages but rewrite H1 to `Funeral and wedding choirs in [City]` (5 chars longer; signals both intents). (2) Split by vertical: `/areas/manchester-funerals.html` and `/areas/manchester-weddings.html` (more pages, more focused, but multiplies the maintenance burden). Path 1 is the lower-cost, higher-confidence win.
- **Effort**: 30 minutes via build template.

#### MEDIUM — Meta descriptions exceed 160 chars on 63 of 99 pages
- **Issue**: Programmatic scan found 63 pages with descriptions over 160 chars. Worst offenders are area pages (250–300 chars) and `pricing.html` (214 chars). Google truncates around 150–160; the rest is wasted.
- **Fix**: Trim to 150–155 chars. Lead with the unique selling point.
- **Effort**: 4–6 hours (manually rewriting 63 descriptions); 1–2 hours if you batch-trim by template and only hand-write outliers.

## 3. Schema markup health

This was the single richest finding area. Schema is everywhere on the site (every page has ≥1 parseable JSON-LD block) but quality issues affect rich-result eligibility.

### What's good

- **All 99 indexable pages have parseable JSON-LD** (verified: zero parse failures across the site).
- **`@id` linking pattern** is used correctly on most pages — `LocalBusiness` has a stable `@id: https://londonchoralservice.com/#organization`, referenced by `provider` blocks.
- **`BreadcrumbList`** hierarchy is correct on all 98 pages that carry it (verified pattern: pillars 2 items, cities 3 items, boroughs 4 items, guides 3 items).
- **`@context: https://schema.org`** consistent.
- **`ItemList`** on `music-guides/index.html` is well-formed (added in commit `c86939c`).

### Findings

#### CRITICAL — `AggregateRating` (`5/4 reviews`) on 99 pages, reviews visible on only 2
- **Issue**: The `LocalBusiness` block on every one of the 99 indexable pages embeds `aggregateRating: {ratingValue: 5, reviewCount: 4, bestRating: 5}`. The actual reviews are rendered in body content **only** on `index.html` and `about.html`. Attaching the same 4-review rating to a music guide about *Abide With Me*, the *Manchester* area page, and the *contact* page is the exact pattern Google's review-snippet policy targets:
  > "Don't… use site-wide markup that aggregates third-party reviews together for the entire site."
- **Risk**: silent suppression (Google ignores all review markup site-wide) → manual action against review snippets. Either way, the rating delivers zero benefit and significant downside.
- **Evidence**: `python3 -c '...'` parsing every JSON-LD block found 99 occurrences. Verified live: `https://londonchoralservice.com/music-guides/abide-with-me.html` and `https://londonchoralservice.com/areas/manchester.html` both contain the rating.
- **Fix**: Keep `aggregateRating` and the `review` array only on `index.html` (where the 4 reviews are shown). Optionally on `about.html`. The other 97 pages should reference `LocalBusiness` by `@id` only:
```json
{
  "@type": "LocalBusiness",
  "@id": "https://londonchoralservice.com/#organization",
  "name": "The London Choral Service"
}
```
- **Validation**: After the fix, run [Rich Results Test](https://search.google.com/test/rich-results?url=https://londonchoralservice.com/music-guides/abide-with-me.html) — should return no review-snippet eligibility errors.
- **Effort**: 1–2 hours via build pipeline.

#### CRITICAL — `ratingCount` used instead of `reviewCount` on `weddings.html` and `funerals.html`
- **Issue**: These two pages use `ratingCount` on their Service-level `AggregateRating`. Google's review-snippet validator accepts only `reviewCount` for AggregateRating. `ratingCount` belongs on `Rating`, not `AggregateRating`.
- **Fix** (if you keep an AggregateRating on these pages at all — which depends on the previous finding):
```json
"aggregateRating": {
  "@type": "AggregateRating",
  "ratingValue": "5",
  "reviewCount": "4",
  "bestRating": "5",
  "worstRating": "1"
}
```
- **Effort**: 5 minutes.

#### HIGH — `HowTo` schema on 9 music guides (deprecated rich result)
- **Issue**: Google removed `HowTo` rich results for desktop in September 2023 and deprecated them fully in late 2023. These 9 blocks generate zero rich-result benefit.
- **Affected files**: `music-guides/memorial-service-planning.html`, `funeral-music-guide.html`, `wedding-ceremony-music.html`, `funeral-choir-guide.html`, `hiring-a-choir.html`, `corporate-carol-service.html`, `office-carol-service-planning.html`, `wedding-choir-guide.html`, `choosing-wedding-hymns.html`.
- **Fix**: Remove the HowTo block on each. The `Article` schema already on these pages is the correct type.
- **Effort**: 30 minutes.

#### HIGH — `Article` missing `image` property on all 33 music guides
- **Issue**: Article rich results require (or strongly recommend, depending on subtype) `image`. None of the 33 guides include it.
- **Fix**: Add to every Article (templated):
```json
"image": {
  "@type": "ImageObject",
  "url": "https://londonchoralservice.com/assets/og-image.png",
  "width": 1200,
  "height": 630
}
```
Per-guide images are better but the global OG image is acceptable.
- **Effort**: 1 hour via build template.

#### HIGH — `services.html` Service node missing required `name`
- **Issue**: The Service entity on this page has only `serviceType`, no `name`. Google requires `name` as a minimum identifier.
- **Fix**: Add `"name": "Live Music for Ceremonies"`. Also align `provider` to use `@id` reference (it currently uses an inline `LocalBusiness` object, inconsistent with every other service page).
- **Effort**: 5 minutes.

#### HIGH — `AggregateOffer` missing `priceValidUntil` on 4 service pages
- **Affected files**: `weddings.html`, `funerals.html`, `corporate.html`, `christmas.html`.
- **Fix**: Add `"priceValidUntil": "2026-12-31"` (or your refresh date) to each.
- **Effort**: 5 minutes.

#### MEDIUM — `VideoObject` missing `duration` (and shared placeholder `uploadDate`)
- **Issue**: 4 VideoObject blocks (1 on `pricing.html`, 3 on `listen.html`). `duration` is recommended for video rich-result eligibility. All 4 share `uploadDate: "2025-01-01"` which is almost certainly a placeholder (one date for four different YouTube videos is implausible).
- **Fix**: Add ISO 8601 duration (`PT3M42S`) and the actual YouTube upload date for each.
- **Effort**: 30 minutes.

#### MEDIUM — `MusicGroup` only on homepage
- **Issue**: The homepage correctly types the primary entity as `["LocalBusiness", "PerformingGroup", "MusicGroup"]`. But `about.html` and `services.html` use only `LocalBusiness`. Given the business is fundamentally a 150-musician ensemble, `MusicGroup` belongs on those pages too — strengthens entity claims for AI-search and Google Knowledge Graph eligibility.
- **Fix**: Add `PerformingGroup` and `MusicGroup` to the @type array on `about.html` and `listen.html`.
- **Effort**: 5 minutes.

#### MEDIUM — `FAQPage` on 86 pages — no Google rich-result benefit, but still useful for AI
- **Issue**: Google restricted FAQPage rich results to government/health-authority sites in August 2023. These 86 blocks no longer earn FAQ rich results for a commercial choir-hire site.
- **Decision required**: Keep (because they help AI/LLM citations on ChatGPT, Perplexity, Google AI Overviews) or remove (lean schema footprint). Recommendation: **keep**, since GEO/AI citation is a strategic priority and the questions on this site are well-targeted (e.g. *"How much does a funeral singer cost in Westminster?"*). Document the intent in a one-line comment so future maintainers know.

#### MEDIUM — `openingHours` legacy string format on `index.html` and `contact.html`
- **Issue**: `"openingHours": "Mo-Fr 09:00-18:00"` is the deprecated string syntax.
- **Fix**:
```json
"openingHoursSpecification": [{
  "@type": "OpeningHoursSpecification",
  "dayOfWeek": ["Monday","Tuesday","Wednesday","Thursday","Friday"],
  "opens": "09:00",
  "closes": "18:00"
}]
```
- **Effort**: 5 minutes.

#### MEDIUM — `legalName` "Alma Consort Ltd" absent from all schema
- **Issue**: The footer on every page and `llms.txt` both disclose that LCS trades as Alma Consort Ltd. The schema doesn't. Adding `legalName` to the canonical `LocalBusiness` entity formalises the operating-name-to-registered-company link.
- **Fix**: Add `"legalName": "Alma Consort Ltd"` to the `index.html` LocalBusiness node.
- **Effort**: 1 minute.

#### MEDIUM — `Service` provider block on city area pages missing `@id`
- **Issue**: City-level area pages (`areas/manchester.html`, `areas/oxford.html`, etc.) have a `provider` sub-object with `name` only — no `@id` linking to the canonical `LocalBusiness`. Borough pages do this correctly.
- **Fix**: Standardise all area-page provider blocks to:
```json
"provider": {
  "@type": "LocalBusiness",
  "@id": "https://londonchoralservice.com/#organization"
}
```
- **Effort**: 30 minutes via build template.

#### LOW — `address` is `addressLocality: "London"` only, missing `postalCode` / `addressRegion`
- **Note**: Correct policy for an SAB to omit `streetAddress`. Adding `addressRegion: "Greater London"` and a `postalCode` (the registered office's, if available) would improve fidelity. Optional.

#### LOW — `Person` schema for Luca Wetherall missing `alumniOf` and `worksFor` structured properties
- **Fix**: Expand the founder Person node on `about.html`:
```json
"alumniOf": {"@type": "Organization", "name": "University of Oxford"},
"worksFor": {"@id": "https://londonchoralservice.com/#organization"}
```

#### LOW — `Organization.sameAs` points only to a Google share-link
- **Issue**: `"sameAs": ["https://share.google/HRgq38OubHmj3Zz9v"]` is a share-link shortener — not a stable canonical Google Maps place URL.
- **Fix**: Replace with the canonical Maps URL (`https://www.google.com/maps/place/…`). Add Companies House URL for Alma Consort Ltd. Add LinkedIn company page if one exists. Add YouTube channel URL.
- **Cross-references**: this also matters for the Person sameAs gap (see GEO findings).
- **Effort**: 1 hour once URLs collected.

## 4. Content + cannibalisation

### What's good

- Content depth is solid across the board: pillars 600–2,200 words (only `contact.html` at 346 is lighter — appropriate for a contact page); area pages 800–1,400 words; music guides 1,400–2,800 words. Nothing obviously thin.
- The music-guides cluster is genuinely useful editorial content — well-structured, factually loaded, with named entities and historical/practical detail. These pages are punching above the site's domain authority.
- llms.txt is unusually well-written.

### Findings

#### HIGH — Recycled testimonials across 7–8 borough pages create geography mismatches
- **Issue**: Programmatic detection found 4 testimonial paragraphs each appearing on 7–8 different borough pages. Specifically, a testimonial attributed to *"Pamela, Hampshire"* appears on multiple London-borough pages, including a Waltham Forest page where the geography mismatch undermines credibility. *"Margaret, Dulwich"* and *"Tony, Surrey"* also recycle.
- **Risk**: Trust signal damage (a careful reader spots that the same testimonials appear on every borough page); duplicate-content signal to Google for inner-tier borough pages with already-thinner unique content.
- **Fix**: Either (a) localise testimonials per borough (collect 3 fresh quotes per borough — multi-month project), or (b) consolidate to one rotating block of testimonials with **no location attribution** so the geography mismatch disappears, then build a separate "Reviews" page that does carry the named-location quotes for trust.
- **Effort**: Option (b) is 2–3 hours; (a) is months.

#### HIGH — Shared "Ensembles for every occasion" pricing paragraph on 26 of 33 borough pages
- **Issue**: The exact same paragraph beginning "Not every occasion calls for the same size of ensemble…" appears verbatim on 26 borough pages. Combined with the recycled testimonials, this means roughly 30–40% of body content on lower-tier borough pages is identical across the cluster.
- **Note**: This pattern is also flagged in [SITE-STOP-SLOP-PLAN.md](SITE-STOP-SLOP-PLAN.md) (item: "Ensembles for every occasion" template H2 on 20+ borough pages). The plan-level fix is already on the user's queue — confirming it's load-bearing for SEO too.
- **Fix**: Replace the shared paragraph with locally-specific ensemble guidance (e.g. "*For Westminster Abbey we typically suggest a sextet or larger to fill the volume; for the smaller chapels in Pimlico a quartet works well.*"). Or move the generic guidance to `pricing.html` and link from each borough page.
- **Effort**: Half a day to several days, depending on how localised you want to go.

#### HIGH — `popular-funeral-hymns.html` FAQ contradicts `abide-with-me.html` on most-requested-hymn claim
- **Issue**: The popular-funeral-hymns FAQPage answer says *The Lord's My Shepherd* is "probably the single most requested funeral hymn." The abide-with-me guide (and the site's own positioning of it) says *Abide With Me* "comes up more often than any other." Both can't be true — and AI engines parsing both pages will produce inconsistent answers.
- **Fix**: Standardise the claim across both pages and the FAQ schema. Suggested formulation: *"Abide With Me and The Lord's My Shepherd are the two most-requested funeral hymns in the UK. Abide With Me is the most-commonly-chosen as a closing hymn; The Lord's My Shepherd is the most widely known."*
- **Effort**: 15 minutes.

#### MEDIUM — Cannibalisation: 3 guides target "wedding hymns"
- **Files**: `be-thou-my-vision-wedding-hymn.html`, `choosing-wedding-hymns.html`, `jerusalem.html`
- **Verdict**: Well-differentiated by intent (specific-hymn vs. how-to-choose), no merge needed. Just verify each has clear, distinct title and H1 framing — they do.

#### MEDIUM — Cannibalisation: 3 guides target "funeral hymns"
- **Files**: `popular-funeral-hymns.html` (hub), `abide-with-me.html`, `be-thou-my-vision-funeral-hymn.html` (spokes)
- **Verdict**: Hub-and-spoke is the right structure. Verify popular-funeral-hymns links out to the named-hymn spokes (it does). Action: also resolve the contradiction flagged above.

#### MEDIUM — Cannibalisation: `hiring-a-choir.html` ↔ `wedding-choir-guide.html`
- **Files**: `music-guides/hiring-a-choir.html` (general), `music-guides/wedding-choir-guide.html` (wedding-specific)
- **Verdict**: Differentiated by intent. Light cannibalisation risk only if title/H1 are too similar. Check titles — they read as `What to Expect When You Hire a Choir` vs. `Wedding Choir Guide` — clear enough.

#### MEDIUM — `weddings.html` and `funerals.html` lack a cleanly extractable answer to the most-asked AI/SEO question
- **Issue**: The most commercially valuable AI-search query is *"how much does a wedding/funeral singer cost in the UK?"*. The answer exists on `pricing.html` and in `llms.txt`. But on `weddings.html` and `funerals.html`, pricing lives inside a `.price-cards` div with no surrounding sentence — an LLM scraping the page reads `£215 Soloist £1,150 Quartet…` with no extractable prose. `corporate.html` does this correctly with an FAQ block: *"A small choir of four singers starts from £1,150…"* — that's a perfect citation passage.
- **Fix**: Add a single paragraph above each price-card block, identical structure to `corporate.html`'s FAQ answer.
- **Effort**: 30 minutes.

#### MEDIUM — `areas/index.html` is thin for its structural importance
- **Issue**: 670 words; no AggregateRating; no FAQPage; reads as a list-of-links page. For a "areas we serve" hub of an SAB serving 50+ named locations, this should have 400–600 words of original editorial content explaining how the service works geographically, lead times for distant cities, the relationship between London-borough coverage and outer cities.
- **Fix**: Expand to 1,000–1,200 words. Add a short FAQ ("How quickly can you arrange singers in Manchester?", "Do you charge travel for outer cities?").
- **Effort**: 2–3 hours.

#### MEDIUM — No visible "Last updated" date on commercial pillars
- **Issue**: Music guides render `Published 2 May 2026` (`.guide-meta`). Pillar pages render no visible date. AI engines weight recency; absent dates cost citations against newer competitor content.
- **Fix**: Add a small `<p class="guide-meta">Last updated: May 2026</p>` directly under the H1 on `weddings.html`, `funerals.html`, `corporate.html`, `christmas.html`, `services.html`, `pricing.html`. Also add `dateModified` to the `Service` schema on those pages.
- **Effort**: 1 hour.

## 5. Local SEO

### Findings

#### CRITICAL — Only 4 reviews sitewide; SAB needs 30+ for competitive local-pack ranking
- **Cross-reference**: Top 5 priority #4. The single highest-leverage off-site action.

#### CRITICAL — GBP `sameAs` is a Google share-link, not a canonical Maps place URL
- **Issue**: The `sameAs` array contains `https://share.google/HRgq38OubHmj3Zz9v` — a share-link shortener. Schema parsers cannot reliably resolve this to a verified GBP listing.
- **Fix**: Replace with `https://www.google.com/maps/place/…` (the stable URL with a place ID). Confirm GBP exists, is verified, and has correct primary category ("Choir" or "Music Service") with secondary categories ("Wedding Service", "Funeral Service").
- **Effort**: 30 minutes once GBP access confirmed.

#### HIGH — NAP phone format mismatch between visible HTML and schema
- **Issue**: Visible HTML and `llms.txt` use `07356 042468`. Schema uses `+447356042468`. Same number, different strings — citation aggregators may create two variants.
- **Fix**: Standardise on E.164 format (`+447356042468`) everywhere, including visible HTML where space allows, or keep visible as `07356 042468` for UK-readability and ensure the schema's `+44` form is the only digital identifier.
- **Effort**: 1 hour.

#### HIGH — Borough-page templating issues (cross-references content section above)

## 13. Supplemental findings (re-run of incomplete specialists)

The first audit pass had 4 specialists return incomplete data: technical, content, performance, and Google. This section records what the re-run with tighter scopes surfaced. None of these findings duplicate items in sections 1–12.

### 13.1 Technical (re-scoped re-run)

**13.1.1 — HIGH — Duplicate-content exposure: every `.html` URL has an extensionless 200-status twin.**

GitHub Pages silently serves the same content at both `/about.html` and `/about` — same body, identical ETag. Verified across 4 spot-checks; the pattern is global to all 96 `.html` URLs in the sitemap. The canonical tag on both variants points to the `.html` form, so Google should consolidate, but two risks remain:

- Crawl budget waste if Googlebot discovers the extensionless paths (e.g. via external backlinks that drop `.html`).
- Any future internal link that omits `.html` will conflict with the canonical signal.

Evidence:
```bash
$ curl -sI https://londonchoralservice.com/about.html  | grep -i etag   # → "69fe5a75-e402"
$ curl -sI https://londonchoralservice.com/about       | grep -i etag   # → "69fe5a75-e402"
```

Fix priority order:
1. (Preferred) Add a Fastly VCL rule: 301 any non-`.html`, non-`/`, non-extension URL to `URL.html`.
2. (Acceptable fallback) Audit every `<a href>` in the repo to confirm only `.html` URLs are used internally so the extensionless variants are never discovered organically. Spot-checks suggest this is already true — no internal `href` to a non-extension page found in sampled files.

**13.1.2 — MEDIUM — HSTS header missing `includeSubDomains` and `preload`.**

Current: `strict-transport-security: max-age=31556952`. Add `includeSubDomains; preload` (set `max-age=63072000`) via Fastly custom response, then submit to [hstspreload.org](https://hstspreload.org).

**13.1.3 — MEDIUM — All security headers absent.**

None of these are present on any sampled URL: `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy`, `Referrer-Policy`, `Permissions-Policy`. Set via Fastly custom VCL — these are not direct ranking factors but they are signals raters and review tools (Mozilla Observatory, Lighthouse "Best Practices") penalise.

**13.1.4 — MEDIUM — `robots.txt` has no `Disallow` for tracking parameters.**

If any inbound link uses `?utm_source=…`, `?gclid=…`, `?fbclid=…`, or `?msclkid=…`, Googlebot crawls the parameter variant as a separate URL. Canonicals consolidate, but crawl-budget burns.

Fix: add to `robots.txt`:
```
Disallow: /*?utm_
Disallow: /*?gclid=
Disallow: /*?fbclid=
Disallow: /*?msclkid=
```

**13.1.5 — LOW — `cache-control: max-age=600` is conservative.**

A static deploy-only site can safely run `max-age=3600` or higher with `must-revalidate`. Improves Fastly hit-rate; no SEO impact.

**13.1.6 — LOW — No IndexNow implementation.**

Free, optional; speeds Bing/Yandex/Naver re-indexing on deploys. Generate a key at indexnow.org, drop `<key>.txt` in repo root, POST changed URLs from `build.sh`.

**Confirmed passing (no action):** HTTP→HTTPS single-hop redirect, www→apex single-hop redirect, canonical accuracy across 5 spot-checks, viewport meta with `viewport-fit=cover`, mobile configuration, real 404 status code, sitemap URL cleanliness, no `rel=prev/next` needed (deprecated by Google in March 2020).

### 13.3 Performance / Core Web Vitals (inline static analysis — PSI agent quota-blocked again)

PSI was unavailable on the re-run as well. Findings here are derived from static analysis of HTML/CSS/asset weights in the repo.

**13.3.1 — HIGH — No font preload on any page.**

`Cormorant Garamond` and `Source Serif 4` are self-hosted as `.woff2` (good — no third-party DNS hit) and `font-display: swap` is set (good — no FOIT). But the fonts are referenced only via `@font-face` inside the inline CSS, with no `<link rel="preload" as="font" type="font/woff2" crossorigin>` in `<head>`. On a cold cache, the browser cannot start font fetches until it has parsed the CSS. LCP for any text-heavy hero (every page on this site) is delayed by one round-trip.

Fix in [partials/nav.html](partials/nav.html) or directly in each `<head>`:
```html
<link rel="preload" href="/fonts/cormorant-garamond.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="/fonts/source-serif-4.woff2" as="font" type="font/woff2" crossorigin>
```

**13.3.2 — HIGH — Images on hero / video sections lack explicit `width` and `height` attributes.**

`grep -c '<img[^>]*width='` returns 0 on `index.html` and 0 on `funerals.html` despite `funerals.html` containing 3 `<img>` tags (the YouTube facade thumbnail among them). Without explicit dimensions, the browser cannot reserve space → CLS spikes when the image loads.

Fix: add `width` and `height` attributes (or aspect-ratio CSS) on every `<img>` and `<picture>` element. The YouTube facade thumbs (`maxresdefault.jpg`) are 1280×720.

**13.3.3 — MEDIUM — Inline CSS is duplicated across all 99 pages.**

Each page is ~1,800–1,970 lines, of which roughly 800–1,000 lines are the inlined `<style>` block (varies by page). This is the same CSS on every page, with no cross-page browser caching. Total over the site: roughly 80–100 MB of duplicated CSS bytes that a single external stylesheet would serve once.

The tradeoff was deliberate (faster TTFB on first visit, no critical-CSS extraction step). For a site of this size it is defensible. But:

- A returning visitor with a warm cache pays the inline CSS cost on every page navigation.
- Lighthouse will flag "Reduce unused CSS" on every page.

Fix (optional): extract the shared CSS to `/style.css`, keep only the above-the-fold critical path inline, link the rest with `<link rel="preload" as="style" onload="this.rel='stylesheet'">`. This is a moderate refactor and only worth doing if real CWV data shows the cost.

**13.3.4 — LOW — No LCP candidate image preload.**

No `<link rel="preload" as="image">` anywhere. Most pages have no above-the-fold image (text hero), so LCP is text — preload not needed. Pages that DO have a hero image (e.g. `pricing.html` carries a `VideoObject` thumbnail) would benefit from preloading the LCP element.

**Confirmed passing:** `font-display: swap` set on all 4 `@font-face` declarations. `loading="lazy"` used on YouTube facade thumbnails (good — defers offscreen image cost). Image inventory is minimal (5 PNGs + 1 SVG total in `/assets/`) — most pages render entirely from text + icons. GA4 + Ads conversion tracking deferred via `requestIdleCallback` (good — verified in `index.html` lines 8–30).
